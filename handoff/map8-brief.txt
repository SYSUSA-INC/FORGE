
######## auth-core
SUMMARY: The auth core runs on Auth.js / next-auth 5.0.0-beta.31 (@auth/core 0.41.2) with Next 14.2.15. Sessions are JWTs with no maxAge set, so the default 30 days applies, and the middleware re-issues the cookie on every request, so the session never expires while in use. There are three providers: Credentials (email and password, bcrypt with 12 rounds), Google, and Microsoft Entra ID. Both OAuth providers have allowDangerousEmailAccountLinking turned on. The Drizzle adapter is used only for OAuth users and accounts. The `session` table is unused, and `verificationToken` has been repurposed by src/lib/tokens.ts.

On the Node side, the jwt callback reads the database on every auth() call to refresh isSuperadmin, organizationId and role. It also reads `disabled` but ignores it.

The middleware enforces no authentication. It wraps auth() around a handler, and next-auth only applies a false result from `authorized` when there is no wrapper. That makes the allow-list in auth.config.ts dead code; the middleware's only job today is blocking writes during impersonation. All real enforcement goes through one function, getSessionUser() (src/lib/auth-helpers.ts:19). Every require* helper and requireApiTenant call it: 897 call sites in 199 files, including all 89 "use server" files, every page except two redirect-only stubs, and the six API routes that use a session. Seven files call auth() directly and decide on their own whether someone is signed in.

That gives one authoritative place to enforce "MFA not yet done": getSessionUser/requireAuth, backed by session state kept server-side and read in the jwt callback. Three other things are needed:
- the seven direct auth() callers must be fixed, because the sign-in, sign-up and request-trial pages would otherwise redirect in a loop;
- the MFA pages need their own gate that accepts a pending session;
- the middleware can be an optional outer layer, but it runs on the edge with no database access, so it would only work after the wrapper bug is fixed and the MFA result is a claim in the JWT.

Areas that need no session today (token-, signature- or secret-authenticated):
- public pages: /pricing, the sign-in, sign-up, forgot-password, reset-password, verify-email and request-trial pages, and /review/[token] with its two server actions;
- public APIs: /api/register, /api/forgot-password, /api/reset-password, /api/trial-request, /api/error-report, /api/samgov/health and /api/auth/*;
- secret- or token-checked APIs: /api/cron/* (13 jobs, Bearer CRON_SECRET), /api/webhooks/stripe and /api/v1/* (workspace API tokens).

Several existing gaps directly affect MFA design:
- Disabled users keep working sessions.
- Neither a password reset nor a forced reset revokes sessions.
- Password sign-in has no rate limit.
- The rate limiter fails open.
- audit_log requires an organization, so events for users with no organization are silently dropped.
- secret-box refuses to run on preview deployments, whose databases are copies of production.
- Entra defaults to the multi-tenant `common` issuer and takes `profile.email`; combined with dangerous account linking, this is an account-takeover path. If MFA is enrolled at first sign-in, a takeover can end with the attacker enrolling their own authenticator.
CONSTRAINTS:
- Enforce in getSessionUser()/requireAuth() (src/lib/auth-helpers.ts:19-29). Every require* helper and requireApiTenant go through it, so one change covers all actions, pages and session-based routes. The middleware cannot be the authoritative gate: it is edge-only on Next 14, the DB client is pg Pool (no DB access), it skips image-extension paths, and today it does not enforce sign-in at all.
- A pending-MFA session must still exist so the challenge page can identify the user. The MFA pages and their actions need a separate gate, e.g. requirePendingSession(), that accepts the pending state. Everything else must treat a pending session as not signed in.
- Never trust the jwt callback's `trigger==='update'` `session` payload. POST /api/auth/session is client-callable with the user's own CSRF token. MFA completion must be read from server-side state (DB), not from client data.
- If the MFA result lives only in the cookie and is written via unstable_update, the middleware re-issues the old cookie on the same request (handleAuth appends Set-Cookie on every request), which can overwrite it. Prefer a server-side session record keyed by a `sid` claim minted in the jwt callback at sign-in (when `user` is present), and read it on each Node-side auth() call. That record also enables revocation by returning null from the jwt callback.
- The sign-in (sign-in/page.tsx:18-21), sign-up (sign-up/page.tsx:23-24) and request-trial (request-trial/page.tsx:15-16) pages redirect any session.user into the app. With requireAuth bouncing pending sessions this would loop, so they must send pending sessions to the MFA step. AppShell.tsx:19 and the public layout and pricing page must not show a pending session as signed in.
- MFA pages must sit outside the (app) route group, because AppShell renders nav and superadmin links from auth(). They need their own sign-out, since UserMenu lives in AppShell. A new redirect target needs a page in the same PR (scripts/check-links.mjs).
- Preserve callbackUrl through the MFA step and pass it through safeRedirectTarget. requireAuth currently drops it.
- requireApiTenant turns any redirect into a generic 401 'Sign in to continue.'. Fetch clients (AI chat/draft/transcribe, uploads) need a distinguishable MFA-required response.
- Token- and secret-authenticated surfaces must stay reachable without MFA: /review/[token] and its two actions, /api/v1/* (workspace API tokens), /api/cron/* (CRON_SECRET), /api/webhooks/stripe, /api/register, /api/forgot-password, /api/reset-password, /api/trial-request, /verify-email, /api/error-report, /api/samgov/health and /api/auth/*. The 8d origin lock must also exempt crons, which call the Vercel deployment directly without the Cloudflare header.
- Brute-force limits on TOTP and recovery codes must fail closed (attempt counter on a DB row). enforceRateLimit fails open (rate-limit.ts:120-124).
- TOTP secrets need encryption at rest. secret-box binds to (purpose, organizationId) and is refused on preview, so it needs a new user-bound purpose. A policy is needed for preview deployments, whose DBs are prod copies; secrets copied to preview must not be usable there.
- Audit rows require organization_id. recordAuthDenied drops org-less events, and superadmins or fresh OAuth users may have no membership. MFA events need resolveAuditOrgForUser-style fallback or a platform-level security log. Follow the '<resource>.<verb>' convention (e.g. user.mfa_enroll, user.mfa_reset, user.mfa_recovery_used, auth.mfa_failed). recordAudit goes after the write and before revalidatePath.
- New MFA and session tables keyed by user_id with no organization_id are not tenant tables for check-isolation or tenant-firewall. They still need matching drizzle/NNNN_*.sql migrations and src/types/next-auth.d.ts additions for any new claims.
- 'use server' files may only export async functions; constants go in a *-constants.ts sibling. Server actions must not take organizationId or userId-to-act-on from the client without an admin gate.
- MFA applies to OAuth sign-ins too, not just credentials. All sessions are minted only at /api/auth/callback/{credentials,google,microsoft-entra-id} (no auto sign-in after register, reset or invite), so the jwt callback's sign-in branch is the single place to mark a session pending.
- The collab service trusts 15-minute HS256 tokens minted by /api/collab/token (requireCurrentOrg). MFA gating covers minting, but a token already issued stays valid until it expires. Any new signed cookie should use a key derived per purpose, not raw AUTH_SECRET, which collab tokens already use.
- Passkeys: Auth.js's built-in WebAuthn provider is an experimental first-factor sign-in provider that needs the adapter's authenticator table. It does not fit a second factor, so a 2FA passkey needs its own library (none installed). RP ID and origin should come from a fixed env (appBaseUrl), not request headers (trustHost:true).
OWNER Qs:
? Passkeys: are they a second factor after the password, or should a passkey alone replace password + TOTP (passwordless)? This changes whether they plug into the jwt/MFA step or become a sign-in provider.
? Session lifetime for sensitive data: sessions currently slide forever (30 days idle, re-issued on every request). Do you want an idle timeout, an absolute maximum session age, and MFA re-prompts (every sign-in only, or also every N hours/days or for sensitive actions such as exports, API-token creation and role changes)?
? Who may reset someone's MFA: only platform superadmins, or also each company's org admin for their own members? Must the person be told by email? Must a reset also sign them out everywhere and require re-enrolment at next sign-in?
? Rollout for existing users: at the first sign-in after release, anyone holding a password (including an attacker with a leaked one) could enrol their own authenticator. Should first enrolment also require an emailed confirmation code, or a grace window with forced enrolment by a date?
? Google and Microsoft sign-ins: should FORGE's own MFA still be required on top of the provider's (owner said every user), or may a provider that proves MFA (Entra `amr` claim) count? Should Microsoft sign-in be limited to known customer tenants rather than the `common` endpoint, and should automatic linking of an OAuth login to an existing account by email be turned off?
? Recovery: when a user loses both the authenticator and the recovery codes, before SMS exists, what is the path: an admin reset only, or an emailed recovery link? An emailed link would make email a single factor for account recovery.
? Preview and staging deployments use copies of production users. Should MFA be enforced there with separate keys (production TOTP secrets unreadable on preview, so testers enrol again), or should previews use separate test accounts?
? Superadmins: should they be required to use a passkey or security key (phishing-resistant) rather than TOTP?
? Disabled users and password resets currently leave existing sessions working. Should disabling a user, resetting a password, or resetting MFA immediately sign out every session? This needs server-side session records.
? Should workspace API tokens (/api/v1) be creatable only by an MFA-verified admin, and should existing tokens be re-confirmed after rollout?
RISKS:
! The middleware sign-in gate has been dead since the impersonation wrapper was added (auth((req)=>...) makes next-auth ignore authorized()=false). Today this is safe only because every page and action calls a helper. Nothing in CI enforces that, so a new ungated page or route ships public. A design that adds MFA to `authorized` would silently do nothing.
! Pre-existing: a disabled user keeps a working, sliding session (src/auth.ts:254-257 ignores enriched.disabled; requireAuth never checks it). Password reset, forced reset and sign-out don't revoke stolen cookies (JWT strategy, no session store).
! Pre-existing account-takeover path: Entra defaults to the `common` issuer, takes the mutable profile.email, and allowDangerousEmailAccountLinking is on for Google and Entra. If MFA is enrolled at first sign-in, an attacker who gets in this way first can enrol their own TOTP and lock the real owner out.
! Pre-existing: no rate limit or lockout on credential sign-in (auth.ts authorize), and enforceRateLimit fails open. TOTP codes (10^6 space) need a fail-closed attempt counter or they can be brute-forced inside the ±1 step window.
! Cookie race: if the MFA result is carried only as a JWT claim and written via unstable_update in a server action, the middleware's Set-Cookie of the old token on the same request may overwrite it. Users would then be stuck in an MFA loop, or the result could be lost or inconsistent.
! Redirect loops: sign-in, sign-up and request-trial redirect any session into the app, while requireAuth would bounce pending sessions back to /sign-in. Both must be MFA-aware. requireAuth also discards callbackUrl.
! Per-request DB cost: auth() is not memoized and already runs 2 queries per call, often twice per request. Adding a session/MFA lookup without React cache() or folding it into enrichFromDb multiplies load on Neon.
! Audit gaps: MFA events for users without an active membership (new OAuth users, superadmins without an org) are silently dropped because audit_log.organization_id is NOT NULL and recordAuthDenied returns early. Sign-ins are not audited at all today.
! Preview deployments hold copies of production users. Storing TOTP secrets unencrypted would copy every user's second factor to every preview branch. Encrypting with secret-box makes MFA unusable on preview unless the design adds a preview policy.
! Next 14.2.15 is below 14.2.25 (CVE-2025-29927: middleware bypass via the x-middleware-subrequest header). Vercel-hosted deployments are reported unaffected, but the AWS/ECS roadmap (docs/architecture/aws-deployment-roadmap.md) would make any middleware-only control (8d origin lock, impersonation write-block, an MFA outer gate) bypassable. Upgrade Next, or strip the header at Cloudflare.
! Behind Cloudflare, x-forwarded-for's first entry becomes a Cloudflare egress IP unless ipFromRequest and audit-log readRequestContext switch to CF-Connecting-IP, and only when the origin-lock header is verified. Otherwise per-IP limits (register 5/h) throttle unrelated users together, and audit IPs become meaningless.
! verify-email consumes its token on a GET page render (email link scanners can burn it), and consumeToken is not atomic (select, then unconditional delete). Reusing these helpers for MFA email codes or recovery links would inherit both problems.
! A collab token already issued and the impersonation cookie survive an MFA reset or revocation for up to 15 and 60 minutes respectively. Workspace API tokens are not tied to any user's MFA state.

######## ways-in
SUMMARY: Every interactive way into FORGE ends in an Auth.js v5 sign-in. That is either the credentials callback or the Google / Microsoft Entra OAuth callback (next-auth 5.0.0-beta.31, JWT sessions, 30-day rolling default).

- **Flows that never create a session.** Sign-up (/api/register), the verify link (/verify-email), password reset (/api/reset-password), invites and trial approvals all just send the person to /sign-in.
- **Where MFA has to go.** There is one choke point: the JWT when it is issued (src/auth.ts:249-260). The check must then be enforced in getSessionUser/requireAuth (src/lib/auth-helpers.ts:19-29), which every server action and API route goes through. Middleware runs at the edge with no DB and only copies `id` into the session, so it can be a second layer at most.
- **Where phone capture and enrolment go.** OAuth users and existing users can only be handled after sign-in, on an interstitial screen. OAuth has no form.
- **Machine and public surfaces that must stay MFA-free.** /api/v1 (API tokens), /review/[token], /api/cron/*, the Stripe webhook, /api/error-report and /api/samgov/health.

What the design has to fix or work around:
- **No session revocation.** A disabled user keeps working: `enrichFromDb` computes `disabled` and nothing uses it.
- **No audit rows for any authentication event.** In addition, audit_log needs an organisation, so events for users without one are dropped.
- **OAuth users never get `emailVerified`,** so the unverified purge can delete them.
- **Silent OAuth account linking.** Google and Entra both have `allowDangerousEmailAccountLinking`; the Entra issuer falls back to the multi-tenant `common` endpoint when its env var is unset; neither provider's email-verified claim is checked.
- **Open redirect.** `callbackUrl=/\evil.com` gets past `safeRedirectTarget`.
- **Ways for someone other than the mailbox owner to set a working password.** This matters because enrolment at first sign-in trusts whoever signs in first:
  - Accepting an invite for an address that already has an account overwrites that account's password, and tenant admins always get the invite link back.
  - Self sign-up overwrites the password of any unverified account, including OAuth-only ones.
  - The superadmin forced reset always returns the reset link to the superadmin.
- **Encrypting TOTP secrets.** The existing secret store (secret-box) is tied to an organisation and refused on preview deployments, whose databases are production copies.
- **Rate limits.** The limiter fails open, and sign-in has no rate limit at all.
- **Behind Cloudflare.** Every IP rate limit and the audit IP would see Cloudflare's edge IP instead of the client's unless the code switches to `cf-connecting-ip`.
CONSTRAINTS:
- Enforce MFA in getSessionUser/requireAuth (Node, DB-aware). Server actions are POSTed with Next-Action to whatever page path is open, including public paths like /sign-in and /review/*, so path rules in middleware cannot protect them. Edge middleware has no DB and today only copies `id` into the session, so treat it as a second layer at most.
- requireApiTenant (src/lib/api-tenant.ts) turns the requireAuth redirect into JSON 401. A new 'MFA required' redirect must also come back as a JSON 401/403, not HTML, for /api/ai/*, /api/uploads/*, /api/collab/token and /api/proposals/*/pdf.
- The Credentials provider forces JWT sessions in Auth.js. MFA state and revocation therefore need either a server-side record referenced from the token (e.g. a sid row read in enrichFromDb, which already runs on every auth() call) or a per-user epoch. Never trust the jwt callback's `session` argument: a client can POST arbitrary data through update().
- Server components cannot set cookies. Upgrading the JWT after a successful MFA check has to happen in a route handler or server action (unstable_update or an equivalent re-issue).
- These must stay reachable without MFA: /api/v1/* (machine tokens), /review/*, /api/cron/* (CRON_SECRET), /api/webhooks/stripe, /api/error-report, /api/samgov/health, and the sign-in, sign-up, verify-email, forgot/reset-password and request-trial pages and their APIs.
- MFA pages must open with an MFA-pending session and must not render AppShell, which calls auth() and shows the nav. Put them under the (auth) layout. The sign-in page redirects any session to callbackUrl, so send MFA-pending sessions to the MFA step without creating a redirect loop. Any new redirect target needs its page in the same PR (check-links.mjs).
- Fix safeRedirectTarget (backslash bypass) before callbackUrl is carried through an MFA step. The file contains raw NUL bytes, so Edit/Write refuse it; change it with a shell command that keeps its encoding, or convert it to UTF-8.
- While the impersonation cookie is set, middleware blocks every non-GET request, including any POST an MFA re-check would need.
- MFA, recovery-code and phone tables are per user, with no organization_id and user_id FK ON DELETE CASCADE, so deleteUserAccount and the purge clean them up. New token purposes (email change, email OTP) must be added to TokenPurpose/LIFETIMES_MS and to dropTokensFor.
- audit_log requires organization_id. Events for users with no org (bootstrap superadmins, invitees before membership, OAuth users before provisioning) are dropped today (recordAuthDenied, resolveAuditOrgForUser, auditPlatform). The design needs a home for them: fan out to every org the user belongs to plus a log line, or a platform-level auth_event table with a documented exception in .tenant-firewall-allow.json like production_error/payment_event.
- TOTP secrets need encryption at rest. secret-box only supports purpose 'samgov_api_key' with organizationId in the AAD, so it needs a user-scoped purpose/AAD. The keyring is refused on previews (prod-copy DBs), so define how sign-in works on previews. Never log or audit seeds, codes or recovery codes (BL-STAB-7b rule).
- New columns on "user" must be nullable or have a DB default, because the adapter's default user table handles OAuth sign-ups. Using Auth.js WebAuthn would need the adapter's default `authenticator` table shape. That provider is experimental and is a first-factor sign-in, not a second factor.
- Schema change and drizzle/0134+ migration ship in the same PR. One PR per slice, under 1,500 LOC; update the BL-STAB-8 entry in docs/BACKLOG.md.
- Audit naming is '<resource>.<verb>' (e.g. auth.mfa_enroll, auth.mfa_verify_failed, user.mfa_reset). Call recordAudit after the write and before revalidatePath; it never throws.
- Invite acceptance, password reset and admin reset must never change or clear MFA enrolment. Because enrolment at first sign-in trusts whoever signs in first, no link-holder or sign-up may set a password on an account that already exists.
- The rate limiter fails open. Limits on MFA code attempts must not: count attempts on the challenge or factor row, or fail closed.
- Turnstile: on sign-in the token arrives as an extra credentials field read in authorize(credentials, request). /api/register, /api/trial-request and /api/forgot-password take it as a JSON field. The invite branch of /api/register shares the endpoint with the self-service branch.
- Behind Cloudflare, read the client IP from cf-connecting-ip only after the origin-lock header has been checked. Change it in both ipFromRequest (rate-limit.ts) and readRequestContext (audit-log.ts). /api/cron/* (Vercel Cron calls the origin directly) and /api/webhooks/stripe must be exempt from the origin lock.
- emailVerified (camelCase column "emailVerified") is the credentials sign-in gate. OAuth never sets it, so making it mandatory on every way in requires backfilling OAuth users and setting it from provider claims.

RISKS:
! Enrolment at first sign-in trusts whoever signs in first, and several paths let someone other than the mailbox owner hold a working password:
- A tenant admin always gets the invite link back (users/actions.ts:291, 335). Accepting it for an address that already has an account overwrites that account's password (register/route.ts:128-138). That user may belong to other workspaces, which makes this a cross-tenant takeover.
- Self sign-up overwrites the password of any unverified account, including OAuth-only users on public or unowned domains, whose emailVerified stays null (371-375). The attacker's password goes live as soon as the address is verified by any path (verify link click, invite attached via OAuth).
- Superadmin forced reset always returns the link.
Close these before or with 8a, or a phished or planted password enrols the attacker's factor.
! There is no session revocation: disabling a user, resetting a password or (in future) resetting MFA leaves existing 30-day rolling JWTs valid. The disabled flag is computed and ignored (auth.ts:54). 8a needs a server-side session id or epoch, and it fixes this existing gap too.
! OAuth linking has the nOAuth weakness: allowDangerousEmailAccountLinking on Entra with an unchecked email claim, and the issuer falls back to multi-tenant 'common' when its env var is unset. An attacker who controls an Entra tenant may be able to sign in as an existing FORGE user, or claim a company domain through provisionOrgForUser. Check the app registration (unverified-email claims removed, xms_edov) or restrict tenants.
! Open redirect in safeRedirectTarget via '/\evil.com'. An MFA step that carries callbackUrl would add another place to exploit it, e.g. phishing straight after a real MFA prompt.
! In open sign-up mode, an unverified sign-up claims the company domain for its new workspace. Real colleagues are then refused at sign-up and trial request ('already on FORGE', with the org name disclosed) until the 7-day purge.
! OAuth-only users count as unverified. The bulk purge can delete legitimate single-user Google/Microsoft workspaces, and an 8b rule of 'verified email on every way in' that reuses emailVerified without a backfill would lock them out.
! Sign-in has no rate limit, and the rate limiter fails open on DB errors. Credential stuffing goes unchecked, and an MFA code limit built on the same helper would allow unlimited guessing during a DB problem (a 6-digit TOTP with ±1 step accepts 3 codes in 10^6 per try).
! Behind Cloudflare, every IP-keyed limit (register 5/h, forgot 5/h, trial 3/h) and the audit IP would see Cloudflare edge IPs, causing mass false 429s. Trusting cf-connecting-ip without the origin lock lets anyone spoof their IP.
! No audit exists for sign-in, sign-up, verification, invite acceptance, OAuth linking or password reset, and audit_log cannot hold rows for users without an org. A takeover today leaves almost no trail.
! Preview deployments use production-copy DBs and cannot decrypt secrets. Under mandatory MFA, nobody can sign in on previews unless a bypass is added, and a bypass that is not strictly limited to previews would be a production hole.
! events.signIn attaches invites (and marks the email verified) and, in open mode, creates workspaces before any MFA step. A password-only attacker still consumes invites and creates tenants unless this moves after MFA.
! OAuth emails are matched case-sensitively by the adapter, so a provider returning mixed case creates a second account. That account would start with no MFA and no memberships, and would enrol fresh.
! An MFA-checked org admin can mint never-expiring API tokens that read all proposal text with no MFA. That makes a compromised admin session persistent.
! The superadmin bootstrap script (scripts/grant-superadmin.mjs) writes no audit row. A superadmin without an org loses every audit row it should produce, including future MFA resets it performs.
! Verify links are spent by GET, so mail-security scanners verify accounts without a person clicking, and the real click then shows 'Verification failed'. Re-verification on email change inherits this unless the flow moves to a POST confirm step.

######## data-crypto
SUMMARY: I read the user data, secrets and libraries area for BL-STAB-8 without changing anything. The `user` table (src/db/schema.ts:59-72) has email, emailVerified, password_hash (bcrypt, 12 rounds), is_superadmin and disabled_at. It has no columns for a phone number, MFA, a session version or the last sign-in. Sessions are JWT-only: the `session` table is never used, the default idle lifetime is 30 days, and nothing can revoke a session. The node jwt callback reloads the user from the database on every auth() call. The edge middleware only sees the user id.

Secrets are stored three ways today:
- **Hashed one way (SHA-256):** email, reset and invite tokens (src/lib/tokens.ts) and API tokens.
- **Encrypted (AES-256-GCM):** company SAM.gov keys, through src/lib/secret-box.ts and the FORGE_SECRET_KEYS keyring. The keyring is refused on preview deployments, and the only purpose it supports is "samgov_api_key", bound to an organizationId.
- **Plaintext:** OAuth tokens in `account` and the review-request tokens.

No code uses timingSafeEqual, and there is no base32 helper.

Rate limiting is a Postgres fixed-window counter that fails open. Only register (5 per hour), forgot-password (5 per hour) and trial-request (3 per hour) are limited, all by IP. Credentials sign-in, reset-password and verify-email have no limit at all.

recordAudit needs an organizationId, so sign-in and pre-membership events can't be audited. No sign-in, failed-sign-in or MFA audit actions exist, and there is no login history.

None of otplib, @simplewebauthn/*, libphonenumber-js or qrcode is installed, not even as a transitive dependency. The useful libraries already present are jose, bcryptjs and node:crypto. The latest migration is 0133, so the next one is 0134. Migrations are hand-written, idempotent SQL that runs automatically at boot, where destructive operations are refused. A table with no organization_id is outside the isolation and firewall gates.

Two things a design must handle:
1. **Possible account deletion (unconfirmed, needs a test).** When someone links Google or Microsoft by email to an existing account, Auth.js still fires `events.createUser`. Under invite_only, with no pending invite, FORGE's handler then deletes that user, and their memberships go with them.
2. **Whoever enrolls first owns the account.** Enrolling MFA at first sign-in means whoever signs in first after launch binds the factor. Combined with unlimited sign-in attempts and email-based OAuth linking, an attacker who has a user's password, or a matching OAuth account, could enroll their own factor before the real user does.
CONSTRAINTS:
- New columns on "user" must be nullable or have a default. The Auth.js adapter's createUser (OAuth) inserts only id/name/email/emailVerified/image, and boot auto-migration refuses destructive changes, so 'required mobile' and 'MFA enrolled' must be enforced in the app, not with NOT NULL.
- MFA factor, recovery-code and passkey tables should be keyed by user_id with no organization_id, because one user spans several tenants. That keeps them out of check-isolation and check-tenant-firewall. If organization_id is added anyway, the firewall rules apply: NOT NULL, FK ON DELETE CASCADE, a leading index, and a pgTable in schema.ts.
- TOTP secrets need reversible encryption, which means secret-box. Extending it means:
- adding a SecretPurpose (e.g. "totp_secret");
- generalising ctx.organizationId to a subject id (the userId) while keeping the AAD format byte-identical for existing samgov rows (`fsb1|samgov_api_key|<orgId>|<kid>`);
- extending re-encryption after rotation to the new purpose.
Plaintext, codes and secrets must never be logged, audited or returned (standards §1 'Secrets at rest'); log.ts will not redact them.
- secret-box is refused on preview deployments, whose database is a copy of production, so TOTP secrets cannot be decrypted there. The design needs an explicit preview policy, such as re-enrolling on the preview, skipping MFA there, or a separate preview keyring; the current standards forbid sharing the prod keyring.
- Recovery codes should be stored one-way, following the existing SHA-256-of-high-entropy-token pattern (tokens.ts, api-tokens.ts), or with bcrypt for short codes. Use is single-shot via an atomic UPDATE ... WHERE used_at IS NULL RETURNING. TOTP comparison should use timingSafeEqual (no precedent in the code), and replay protection needs the last accepted time-step stored per factor.
- The MFA gate has to work at two layers:
- **Edge middleware** (authConfig, JWT claims only, no DB): its session callback today copies only `id`, so an MFA claim must be copied there for the `authorized` callback to see it.
- **Node getSessionUser/jwt callback** (DB-enriched on every call): it must derive MFA state from server-side truth, never from a client-supplied update payload.
- The MFA enroll and verify routes need a signed-in but MFA-pending session. They must not be added to the public-path list in auth.config.ts. The seven direct auth() callers must treat a pending session as not signed in; for example, sign-in/page.tsx:18 redirects any session onward and would loop.
- Paths that don't use a session are outside MFA by design: /api/v1 (bearer API tokens), /api/cron (CRON_SECRET), /api/webhooks/stripe, /review/ token pages and /api/error-report. The collab token mint goes through requireCurrentOrg, so it inherits the node gate.
- recordAudit needs an organizationId. Sign-in and MFA events for users without a membership cannot go to audit_log; that needs a new user-level table or a log. An admin MFA reset should write to the target user's organization(s), not to the actor's (unlike resolveAuditOrgForUser).
- Because sessions are JWTs, revoking them on MFA reset, password reset or disable needs a per-user epoch/version column checked in the jwt callback. Nothing like that exists today.
- If the jwt callback reads new MFA columns and the query fails, it must fail CLOSED. safeQuery-style fallbacks that return 'no MFA needed' would be a bypass.
- The rate limiter fails open. MFA code attempts need a hard per-user/per-factor attempt cap (e.g. a counter on the factor row) rather than relying on enforceRateLimit alone.
- Client IP is read in two places, rate-limit.ts:136 ipFromRequest and audit-log.ts:175 readRequestContext. Both must switch together to CF-Connecting-IP, and only when the Cloudflare origin-lock header has been verified.
- Migrations are 0134 and up: hand-written, idempotent, with a header comment and schema.ts in the same PR, and every index declared in schema.ts (check:drift).
- "use server" files may export only async functions. Constants and pure logic go in *-logic.ts / *-constants.ts modules (see api-tokens-logic.ts, samgov-key-logic.ts) so they can be unit-tested; vitest aliases server-only to a mock.
- A diff must stay under 1,500 LOC. 8a probably needs splitting, e.g. (1) TOTP, recovery codes and the session gate; (2) admin reset, audit and session revocation; (3) passkeys.
- Neither otplib, @simplewebauthn/*, libphonenumber-js nor qrcode is installed. Each one added is a new dependency for review. TOTP can be built on node:crypto, but QR rendering, WebAuthn and E.164 parsing realistically need libraries. Auth.js's built-in Passkey provider is a primary (passwordless) sign-in method, not a second factor.

######## edge-infra
SUMMARY: I read the request edge and infrastructure code for BL-STAB-8 and changed nothing. FORGE sends no security headers today. next.config.mjs has no headers() function, vercel.json holds only 13 crons, and middleware returns a bare NextResponse.next(). There is no CSP, HSTS, frame-ancestors or Permissions-Policy, and nothing reads cf-connecting-ip. Client IP is read by two separate functions, ipFromRequest in rate-limit.ts and readRequestContext in audit-log.ts. Both take the first x-forwarded-for entry, then x-real-ip. That IP keys the per-IP limits on sign-up (5/h), trial request (3/h), forgot-password (5/h) and error-report (60/h). It is also written to audit_log.ip and trial_request.source_ip. Behind Cloudflare that header would hold a Cloudflare edge IP, if I recall Vercel's docs correctly (they say Vercel overwrites it with the connecting IP). Every user arriving through the same Cloudflare edge address would then share one rate-limit bucket. So the IP helper has to ship before or with the DNS move, and should trust cf-connecting-ip only once the origin-lock header has been checked. A strict CSP mostly fits the code. Fonts are self-hosted, and there are no third-party scripts, analytics, Stripe.js or iframes. The only inline script is the theme boot script in layout.tsx. Next 14.2.15 picks up a nonce from the content-security-policy request header that middleware sets. The CSP must still allow: about 151 server-rendered inline style attributes (so style-src needs 'unsafe-inline'); the R2 upload host https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com in connect-src; the collab wss URL; data: images and Google avatar images; any image URL a user types into the editor; and challenges.cloudflare.com for Turnstile. One existing gap matters here. The proposal export route can serve a stored HTML render inline from the app's own origin, and that render contains raw HTML written by tenant admins in templates. That route needs its own sandboxing CSP. The public forms are sign-up, request-trial, forgot-password and reset-password, which all post JSON to /api routes, and sign-in, which goes through NextAuth Credentials. Sign-in and reset-password have no rate limit at all. Routes the origin lock and Cloudflare bot and WAF rules must still let through: /api/cron/* (Bearer CRON_SECRET), /api/webhooks/stripe (signature-checked), /api/v1/* (API tokens) and /api/samgov/health (uptime probes). One Cloudflare limit is a concrete risk. On plans below Enterprise, Cloudflare gives up on a request after 100 seconds with no response (HTTP 524). ######## CRITIC
SUMMARY: I checked the five maps against the code. Their core is right: all real enforcement goes through getSessionUser()/requireAuth() in src/lib/auth-helpers.ts. The middleware never applies authorized(): auth((req)=>...) passes a wrapper, so handleAuth runs the wrapper instead of redirecting. And auth() called with no arguments (pages, server actions and route handlers alike) throws away Set-Cookie.

Corrections:
1. There are 90 "use server" files (89 files plus the inline sign-out in UserMenu), not 100. The only one with no gate is UserMenu.tsx; the other exports with no gate are harmless.
2. The data-crypto "PLAUSIBLE" account-deletion risk is real, confirmed by reading @auth/core 0.41.2 (not by running it). On the link-by-email path it sets user = userByEmail and then always calls events.createUser before linkAccount. Under invite_only, with no pending invite, FORGE's handler deletes that existing user (memberships cascade), and linkAccount then hits a foreign-key error.
3. New, same code path: the disabled-user check in callbacks.signIn is bypassed on a first OAuth link, because Auth.js hands it a random UUID instead of the FORGE user id.
4. Several maps describe the middleware as "everything else needs !!auth?.user" and treat a JWT claim plus authorized() as the gate. That callback's result is ignored, and the edge session callback drops every claim except id.
5. A design keyed on iat/jti fails: Auth.js re-stamps iat and jti on every middleware refresh. "Revoke tokens issued before T" would stop working after one request.
6. Never delete session.user in the session callback. next-auth's getSession then fills user with the whole decrypted JWT, which still carries id, so the user would look signed in.

Additions a mandatory-MFA design needs:
- **Impersonation deadlock.** While the impersonation cookie is set, the middleware 403s every POST, including the credentials sign-in, OAuth sign-in start, the UserMenu sign-out action and any MFA verify action. The cookie survives sign-out for up to an hour.
- **Enrolment is a takeover path.** Server actions can be called from any page, so a password-only pending session could add its own factor unless enrolment is refused once a confirmed factor exists.
- **Route handlers that return 307 to HTML.** collab/token, the proposal PDF route, the admin export and impersonation/end call require* directly. A pending session gets an HTML redirect there, not JSON.
- **No current path in requireAuth.** Keeping callbackUrl needs a header forwarded by middleware (with any client copy stripped) or the Referer.
- **Things that keep running as a revoked user.** Queued background_job, ai_brief and scout_run rows keep acting as requested_by_user_id. Open collab websockets are authenticated only once, at connect.
- **Security page location.** /settings is behind requireCurrentOrg, so a personal security page there is unreachable for people with no workspace.
- **Theme test on (auth).** tests/design/theme-tokens.test.ts scans all of src/app/(auth) for #RRGGBB. QR colours matter there.
- **Mobile.** No e2e or mobile tests exist. aur-input is 14px, so iOS zooms on focus. The sign-in card leaves about 247px of content width at 375px.
- **Rollout.** Existing cookies carry no sid. Return null from both the node and edge jwt callbacks when sid is missing. This signs everyone out cleanly, makes them re-enter a password before enrolling, and leaves AUTH_SECRET alone; rotating AUTH_SECRET would also break the collab service.

How other Auth.js setups do a second factor:
- **(A) JWT claim plus middleware redirect, upgraded through update().** Here that runs into the dead wrapper, the claims the edge drops, the client-callable update trigger and a possible double Set-Cookie.
- **(B) A server-side session row keyed by a sid claim** (Lucia / Better Auth style). This is the best fit: revocation, sign-out everywhere and last sign-in come with it.
- **(C) No session until the second factor is done,** using an MFA ticket and a second Credentials provider; CredentialsSignin's code comes back to the client as res.code. For OAuth this is awkward: the signIn callback runs before the user is created or linked.
